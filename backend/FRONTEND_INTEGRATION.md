## 1. How the frontend talks to the backend

- All network calls live in **`js/api.js`**. It has `const MODE = "mock"` at the top. In mock mode data is kept in the browser's localStorage. When the backend is ready, set `MODE = "live"` — no other frontend file changes.
- In live mode the frontend calls **relative URLs under `/api`** with `credentials: "same-origin"`. So **Flask must serve both the HTML files and the API from the same origin** (no CORS needed).
- Request bodies are JSON. Updates use **`PATCH`** (partial update).
- On error the frontend reads `json.error` (or `json.message`) and shows it to the user, so error messages should be short, human-readable English sentences.
- Field names in JSON must be **exactly** the column names in section 2 (`id`, `name`, `price_per_day`, `driver_license_no`, ...).

## 2. Target database schema (decision: use this one)

The team agreed on five extra fields, and the frontend uses the naming below.

> ⚠️ The schema currently on `main` (`backend/schema.sql`) is **different** and must be replaced:
>
> | Currently on main | Target |
> |---|---|
> | `car_id`, `customer_id`, `rental_id`, `payment_id`, `user_id`, `role_id` as primary key names | Primary key column is **`id`** in every table. Foreign keys keep descriptive names (`customer_id`, `car_id`, `rental_id`, `user_id`, `role_id`). |
> | `customers.full_name` | `customers.name` |
> | roles `Admin`, `Manager`, `Employee` | roles **`admin`** and **`customer`** (lowercase; the frontend checks `role === "admin"` / `role === "customer"`) |
> | no `customers.user_id` | `customers.user_id` FK → users, UNIQUE, nullable |
> | no `customers.driver_license_no` | `customers.driver_license_no` NOT NULL UNIQUE |
> | no `rentals.total_price` | `rentals.total_price` NUMERIC NOT NULL |
> | no `rentals.status` | `rentals.status` Pending / Active / Completed / Cancelled |
> | no `payments.payment_date` | `payments.payment_date` DATE NOT NULL DEFAULT CURRENT_DATE |

Why the five fields exist:

- `customers.user_id` (FK, UNIQUE): links a login account to a customer, so a logged-in customer sees only their own rentals. Nullable for walk-in customers created by an admin.
- `customers.driver_license_no` (UNIQUE): renting a car requires a driver license.
- `rentals.total_price`: stores the price at booking time, so changing a car's `price_per_day` later doesn't change old rentals, and the remaining balance can be calculated.
- `rentals.status`: separates pending, active, completed and cancelled rentals.
- `payments.payment_date`: needed for the monthly revenue report (GROUP BY query).

Replace `backend/schema.sql` with:

```sql
-- NEW EMPTY DATABASE ONLY. Do not run over an existing database.
CREATE TABLE IF NOT EXISTS roles (
 id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
 role_name VARCHAR(20) NOT NULL UNIQUE CHECK (role_name IN ('admin','customer'))
);
CREATE TABLE IF NOT EXISTS users (
 id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
 username VARCHAR(50) NOT NULL UNIQUE,
 password_hash VARCHAR(255) NOT NULL,
 role_id INTEGER NOT NULL REFERENCES roles(id) ON DELETE RESTRICT
);
CREATE TABLE IF NOT EXISTS cars (
 id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
 brand VARCHAR(100) NOT NULL,
 model VARCHAR(100) NOT NULL,
 license_plate VARCHAR(30) NOT NULL UNIQUE,
 year INTEGER NOT NULL CHECK (year BETWEEN 1886 AND 2100),
 price_per_day NUMERIC(12,2) NOT NULL CHECK (price_per_day >= 0),
 status VARCHAR(20) NOT NULL DEFAULT 'Available' CHECK (status IN ('Available','Rented','Maintenance'))
);
CREATE TABLE IF NOT EXISTS customers (
 id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
 -- Optional 1:1 link to a login account; walk-in customers added by staff have none.
 user_id INTEGER UNIQUE REFERENCES users(id) ON DELETE SET NULL,
 name VARCHAR(150) NOT NULL,
 email VARCHAR(255) NOT NULL UNIQUE,
 phone VARCHAR(30) NOT NULL,
 driver_license_no VARCHAR(30) NOT NULL UNIQUE
);
CREATE TABLE IF NOT EXISTS rentals (
 id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
 customer_id INTEGER NOT NULL REFERENCES customers(id) ON DELETE RESTRICT,
 car_id INTEGER NOT NULL REFERENCES cars(id) ON DELETE RESTRICT,
 start_date DATE NOT NULL,
 end_date DATE NOT NULL,
 total_price NUMERIC(12,2) NOT NULL CHECK (total_price >= 0),
 status VARCHAR(20) NOT NULL DEFAULT 'Pending' CHECK (status IN ('Pending','Active','Completed','Cancelled')),
 CONSTRAINT rental_date_order CHECK (end_date >= start_date)
);
CREATE TABLE IF NOT EXISTS payments (
 id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
 rental_id INTEGER NOT NULL REFERENCES rentals(id) ON DELETE RESTRICT,
 payment_date DATE NOT NULL DEFAULT CURRENT_DATE,
 amount NUMERIC(12,2) NOT NULL CHECK (amount >= 0),
 payment_method VARCHAR(10) NOT NULL CHECK (payment_method IN ('Cash','Card')),
 payment_status VARCHAR(10) NOT NULL CHECK (payment_status IN ('Paid','Pending'))
);
CREATE INDEX IF NOT EXISTS rentals_car_dates_idx ON rentals(car_id, start_date, end_date);
CREATE INDEX IF NOT EXISTS payments_rental_idx ON payments(rental_id);
CREATE INDEX IF NOT EXISTS users_role_idx ON users(role_id);
```

Entity count for the report: roles, users, cars, customers, rentals, payments = **6** (within 5–10).

## 5. Response format (keep the current style)

| Request | Success response |
|---|---|
| `GET /api/<resource>` | `{"status":"success","<resource>":[ ...rows ]}` e.g. `{"status":"success","cars":[...]}` |
| `GET /api/<resource>/<id>` | `{"status":"success","<singular>":{...}}` – singular keys: `car`, `customer`, `rental`, `payment` |
| `POST /api/<resource>` | `201`, `{"status":"success","record":{...}}` |
| `PATCH /api/<resource>/<id>` | `{"status":"success","record":{...}}` |
| `DELETE /api/<resource>/<id>` | `{"status":"success","deleted_id":<id>}` |
| any error | proper HTTP status + `{"status":"error","error":"Human readable message."}` |

`<resource>` is one of `cars`, `customers`, `rentals`, `payments`.

- Numbers (`NUMERIC`) as JSON numbers, dates as `YYYY-MM-DD` strings (the current `serialize()` already does this).
- Never return `password_hash`.
- Map database errors to friendly messages: unique violation → 409 (`"License plate already exists."`, `"E-mail already registered."`, `"Driver license number already registered."`); foreign-key RESTRICT on delete → 409 (`"Car has rentals and cannot be deleted."`).
- **Remove `users` and `roles` from the generic CRUD `CONFIG`.** Right now `/api/users` can be listed and created by anyone. Accounts are created only through `/api/auth/register` (and optionally an admin-only endpoint).

## 6. New endpoints the frontend calls

### 6.1 Authentication (session cookie)

Use Flask's signed session cookie (`session["user_id"]`). Set `app.secret_key` from the environment variable `SECRET_KEY`; set `SESSION_COOKIE_HTTPONLY=True` and `SESSION_COOKIE_SAMESITE="Lax"`. Verify passwords with `werkzeug.security.check_password_hash`.

The **user object** returned by login/register/me always has this shape:

```json
{"id": 2, "username": "demo1", "role": "customer", "customer_id": 1, "name": "Demo Customer One"}
```

`customer_id` and `name` come from the linked `customers` row (`customers.user_id = users.id`); for an admin `customer_id` is `null` and `name` is the username.

| Endpoint | Body | Success | Errors |
|---|---|---|---|
| `POST /api/auth/login` | `{"username","password"}` | `{"status":"success","user":{...}}`, sets session | 401 `"Wrong username or password."` (same message for unknown user and wrong password) |
| `POST /api/auth/register` | `{"name","email","phone","driver_license_no","username","password"}` | 201, `{"status":"success","user":{...}}`, sets session | 400 validation, 409 `"Username is taken."` / `"E-mail already registered."` / `"Driver license number already registered."` |
| `POST /api/auth/logout` | – | `{"status":"success"}`, clears session | – |
| `GET /api/auth/me` | – | `{"status":"success","user":{...}}` | 401 if not logged in |

Register rules: always creates role `customer` (never trust a role from the body); creates the `users` row and the `customers` row **in one transaction**; password ≥ 8 characters; username 3–50 chars `[A-Za-z0-9_.]`; email lowercased; `driver_license_no` uppercased.

### 6.2 Availability (public, no login)

| Endpoint | Success |
|---|---|
| `GET /api/cars/available?start=YYYY-MM-DD&end=YYYY-MM-DD` | `{"status":"success","cars":[...]}` – cars whose status is not `Maintenance` and that have **no** `Pending`/`Active` rental overlapping `[start, end]` (inclusive). 400 if dates are missing or `end < start`. |
| `GET /api/cars/<id>/booked` | `{"status":"success","ranges":[{"start_date":"...","end_date":"..."}]}` – date ranges of that car's `Pending`/`Active` rentals. **Return only dates**, no customer data. 404 if the car doesn't exist. |

Overlap rule (inclusive): `existing.start_date <= :end AND :start <= existing.end_date`.

Register these two routes **before** the generic `/api/<table>/<id>` routes so Flask doesn't treat `available` as an id.

## 8. Business rules

### 8.1 Creating a rental
- For a **customer**: ignore any `customer_id`, `status` and `total_price` in the body. Use the session's `customer_id`, set `status = 'Pending'`, and calculate `total_price` on the server.
- For an **admin**: `customer_id` is required; `status` optional (default `Pending`); `total_price` optional (calculated if missing).
- `total_price = (end_date - start_date + 1) × cars.price_per_day` (inclusive days).
- Reject `end_date < start_date` (400), `start_date` in the past for customers (400), car in `Maintenance` (409 `"This car is under maintenance."`), overlap with another `Pending`/`Active` rental of the same car (409 `"This car is already booked for those dates."`).
- Do the overlap check and the insert in the same transaction (lock the car row with `SELECT ... FOR UPDATE`) so two people can't book the same dates at once.
- `Cancelled` and `Completed` rentals never block a car.

### 8.2 Updating a rental
- Allowed status transitions: `Pending → Active | Cancelled`, `Active → Completed`. Reject others with 400.
- If dates or car change, re-run the overlap check (excluding the rental itself) and recalculate `total_price` unless the admin sends one.

### 8.3 Payments
- `payment_date` defaults to today.
- Remaining balance of a rental = `total_price − SUM(amount WHERE payment_status = 'Paid')`. Optionally include `paid_amount` and `remaining` in each rental object returned by `GET /api/rentals` — the "My rentals" page will show them if present.
- Reject a payment whose `amount` would make the paid total exceed `total_price` (400).

### 8.4 Car status
`cars.status` is managed by the admin (`Available` / `Rented` / `Maintenance`). Availability for booking is decided by the date-overlap rule, not by `Rented`.

## 9. Report queries (`backend/queries.sql`)

Rewrite for the new column names and keep exactly these kinds (the guideline requires them). Suggested:

1. **JOIN** – rentals with customer and car: `rentals r JOIN customers c ON c.id = r.customer_id JOIN cars ca ON ca.id = r.car_id`, showing `c.name`, `ca.brand`, `ca.model`, dates, `r.total_price`, `r.status`.
2. **GROUP BY + ORDER BY** – monthly revenue: `SELECT to_char(payment_date,'YYYY-MM') AS month, COUNT(*), SUM(amount) FROM payments WHERE payment_status='Paid' GROUP BY 1 ORDER BY 1;`
3. **Subquery** – cars priced above average (`WHERE price_per_day > (SELECT AVG(price_per_day) FROM cars)`), or customers with an unpaid balance.

The admin dashboard will show these, so optionally expose them read-only (admin only) as `GET /api/reports/monthly-revenue` etc.
